# kernel 核心结构体关系图

面向学习：讲清 `Plan` / `Node` / `Run` / `Scheduler` 这几个核心结构体各自是什么、谁依赖谁、如何协作。

---

## 一、先建立一个类比（最关键）

这几个结构体分属**图纸**和**施工**两个层面，混在一起看才会懵。先用盖房子类比：

| 结构体 | 类比 | 属于哪层 |
|---|---|---|
| `Plan` | 一张**建筑施工图纸** | 🟦 图纸层（静态） |
| `Node` | 图纸上的**一道工序 / 一个房间** | 🟦 图纸层（静态） |
| `Run` | 按图纸**盖一栋楼**的整个施工过程 | 🟨 执行层（动态） |
| `Scheduler` | **施工队 / 工头**，负责推进施工 | 🟨 执行层（动态） |

一句话：**`Scheduler`（工头）拿着 `Plan`（图纸），开工盖出一栋楼 `Run`（一次施工）。同一张图纸可以盖很多栋楼**（源码注释原话："一个 Plan 可被多个并发 Run 复用"）。

                        │  maxWaves        ← 防死循环上限           │

                        │  commitMu        ← 串行化提交锁           │

                             ▼
   ┌──────────────────────────────────────────────────────┐
   │                    Run  (一次施工/一栋楼)               │
   │  ──────────────────────────────────────────────────  │

   └──────────────────────────────────────────────────────┘
                                 │  Run.Plan 指向
                                 ▼
   ┌──────────────────────────────────────────────────────┐
   │                    Plan  (施工图纸/静态蓝图)            │
   │  ──────────────────────────────────────────────────  │
   │  Name / Entry(入口节点) / Channels(状态合并规则)        │
   │  nodes   map[id]*Node ──┐  一堆节点                   │

## 三、最关键的一点：静态 vs 动态分家

这是最容易懵的地方，单独拎出来讲：

```
       🟦 图纸层 (Plan / Node)              🟨 执行层 (Run)
       ─────────────────────              ─────────────────
       Node.ID       "查天气"      ──────►  Run.NodeStates["查天气"] = {
       Node.Body     怎么干的逻辑              Status:  completed,   ← 跑完没
       Node.Retry    重试策略                  Output:  "晴 25℃",   ← 结果
       Node.Join     汇合规则                  Attempts: 1,         ← 试了几次
       (所有 Run 共享，永不改变)              }
                                            (每栋楼各有一份，随施工变化)
```

- **`Node` 里只有"这道工序是什么、该怎么干"**（静态，所有 Run 共享同一份，永不修改）；
- **"这道工序在这栋楼里跑成什么状态了"存在 `Run.NodeStates` 里**（动态，每个 Run 各一份）。

所以像 `settle` 里的 `st.Status != NodePending`、`Ready` 里的 `run.IsPending(key)`——查的都是 **`Run` 这一侧的动态状态**，而不是 `Node`。

## 四、串起来：一次执行的数据流

```
你调用:  scheduler.Run(plan, "查明天天气", input)
             │
             │ ① 工头拿图纸，新建一栋楼
             ▼
         创建 Run{ Plan: plan, Task:..., Shared:..., NodeStates:{} }
             │
             │ ② drive(plan, run) 进入波循环
             ▼
   ┌──── 每一波 ──────────────────────────────────────────┐
   │ plan.Ready(run)   图纸+当前楼况 → 算出这批跑哪些Node    │
   │        │                                              │
   │        ▼                                              │
   │ node.Body.Run(input, ctx) → Outcome   真正干活         │
   │        │   (Body 内部可能调 run.Llm / run.Tools)       │
   │        ▼                                              │
   │ 屏障: Outcome.StateDelta 合并进 run.Shared             │
   │       Outcome.Control(Goto/Send) 改下一波              │
   │       每步 commit → eventlog (事实) + run.Apply (改状态)│
   └───────────────────────────────────────────────────────┘
             │
             │ ③ 没有就绪节点了
             ▼
         settle → RunCompleted(成功) / RunFailed(卡死)
             │
             ▼
         返回 *Run  (里面有 Shared 最终状态、FinalOutput、Metrics)
```

## 五、一句话记忆法

> **`Plan` 装 `Node`（图纸画工序，静态、可复用）；`Scheduler` 读 `Plan` 造出 `Run`（工头照图纸盖楼）；`Run` 持有指向 `Plan` 的指针 + 所有动态状态（这栋楼的施工进度）；`Node.Body` 是工序里真正干的活，产出 `Outcome` 交回给波屏障合并进 `Run`。**

依赖方向（谁指向谁）：

```
Scheduler ──造/驱动──► Run ──.Plan 指向──► Plan ──.nodes 包含──► Node ──.Body──► NodeBody
    │                    │
    └──都依赖──► ports(Llm/Tool) + Bus + EventLog + BlobStore （外部世界的接口）
```
